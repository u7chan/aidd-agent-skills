# 設計

## 目的

アーキテクチャ、データ、API、UI、運用、非機能要件に関わる設計を扱う。
既存のドメインモデル、用語、ADR、コードと照合しながら、設計案の妥当性・トレードオフ・未決定事項を詰める。
ADR 作成が目的の場合も、まず意思決定として記録すべき内容かを確認する。

## 初動

選択肢、判断基準、トレードオフ、制約、将来の変更コストを明示する。

まず既存資料とコードを探し、ユーザーの説明と照合する。

- `CONTEXT.md`
- `CONTEXT-MAP.md`
- `docs/adr/`
- 既存の設計資料、仕様書、Issue、README
- 関連する実装コード、テスト、設定

目的が曖昧な場合は、最初に今回詰めたい対象を一つだけ確認する。

```md
質問: 今回の設計では、主に何を決めたいですか？

選択肢:
  1. アーキテクチャ方針
  2. データモデル・状態管理
  3. API・外部連携
  4. UI・ユーザー体験
  5. 運用・非機能要件
  6. ADR に残す意思決定
```

## 設計観点

ADR は、覆しにくく、背景なしでは意外で、本物のトレードオフがある採択済みの意思決定だけを候補にする。

- 質問は一度に一つずつ行う。
- コードベースや既存ドキュメントの調査で答えが得られる場合は、質問する前に調査する。
- 不明点が複数ある場合は、依存関係の上流にあるものから確認する。
- 既存資料やコードとの矛盾を見つけたら、設計を進める前に明示する。
- 設計上のリスク、未決定事項、暗黙の前提、将来の変更コストを優先して掘り下げる。
- 複数案がある場合は、判断基準を先に置いてから比較する。
- 「採用しない案」も、重要なトレードオフがある場合は理由を残す。
- 用語や業務ルールの整理が主目的になった場合は、`references/02-define.md` に寄せる。
- 検証しないと判断できない不確実性が主題になった場合は、`references/04-validate.md` に寄せる。

### ADR 判定

ADR を作成・更新する場合は `references/03-design-adr-format.md` を参照する。

次のすべてを満たす場合だけ ADR 候補にする。

1. 後から変更するコストが高い。
2. 理由を知らないと不自然に見える。
3. 複数案のトレードオフを経て決定した。

次の場合は ADR 化しない。

- 流行、標準、慣れだけを理由にした選定
- 局所的なライブラリや開発ツールの採用
- 差し替えコストが低い選定
- README、Issue、PR の説明で十分な選定
- 採択前の検討メモや調査結果そのもの

## 出力

目的に応じて、次の要素から必要なものだけを出す。

- 決定事項
- 背景と制約
- 判断基準
- 比較した選択肢
- 推奨案と理由
- 採用しない案と理由
- 影響範囲
- リスクと未決定事項
- 検証が必要な仮説
- ADR 候補かどうか

ADR として出す場合は、5〜15行程度を目安に「何を決めたか」と「なぜ決めたか」だけを書く。
詳細な設計、調査ログ、実装手順は ADR に入れず、必要なら別の成果物として分ける。
