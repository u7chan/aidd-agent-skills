# 概要

計画・設計・Issue をもとに、実装、検証、記録更新、PR作成までを自律的に進める。
`/dev-start <plan|issue|progress tracker>` で起動する。

## 方針

- 入力された `plan`、`issue`、`progress tracker` から目的、対象範囲、完了条件、検証方法、更新対象を特定する。
- 必要な情報はコード、Issue、設計資料、進捗管理表から調査し、可能な限り追加確認せず進める。
- 確認は、破壊的変更、外部影響が大きい判断、重大な仕様不明点、複数案で成果物が大きく変わる場合に限る。
- 既存変更を確認し、ユーザー作業を壊さない。

## 停止条件

以下の場合のみ停止して判断を求める。

- 要件、完了条件、対象リポジトリ、対象 Issue が不明。
- 破壊的変更、履歴改変、無関係な変更が必要。
- 自力で解決できない問題は最大3回まで対応を試み、それでも解決できない。
- push、PR 作成が認証、権限、保護ルールで失敗した。

停止時は、状況と必要な判断だけを簡潔に伝える。

## ワークフロー

### 1. 作業ブランチ

`main`、`master`、`develop` では作業せず、作業内容に合うブランチへ切り替える。
未コミット変更がある場合は差分を確認し、今回作業と無関係または判断不能なら停止する。
既存ブランチは、今回の作業専用と明確に判断できる場合のみ使用する。

- 形式: `<type>/<description>` または `<type>/<scope>-<description>`
- type: `feature` / `fix` / `docs` / `refactor` / `test` / `chore`
- 小文字・ハイフン区切り・3〜5語を目安にする。
- issue番号やモノレポのscopeがある場合は含める。

### 2. 進捗管理表確認

`progress tracker` を確認し、対象タスク、完了条件、更新箇所を特定する。
既存規約がない場合、`progress tracker` はリポジトリ外の `/tmp/aidd-agent/task-{identifier}-{timestamp}.md` を既定の作成先とする。
存在しない場合は、既存規約から判断できる場合のみ作成する。

### 3. 実装

- 関連ファイル、設定、テストを読み、既存パターンに合わせて変更する。
- 変更は Issue や指示の範囲に絞り、ついでのリファクタや関係ない整形は避ける。
- 複数領域にまたがる場合は、検証しやすい単位で進める。
- 生成物やロックファイルは、必要な場合のみ更新する。
- 実装単位ごとに必要な確認を行い、意図した差分だけを適切な粒度でコミットする。
